# Slay the Spire 2: Ironclad

Use this skill when choosing Ironclad combat actions, cards, potions, rewards, purchases, events, relics, or map routes, or when changing the Ironclad agent.

First identify the installed game branch/version and read the current state. Prefer current in-game/Mod values for card text, costs, enemy intents, legal targets, rewards, shop inventory, and map edges. Do not apply Beta values to Main. Consult [the Ironclad playbook](references/ironclad-playbook.md) for situation-specific combat, upgrade order, and build pivots; [strategy notes](references/ironclad-strategy.md) for broader run decisions; and [decision contract](references/decision-contract.md) when using the MCP providers. Source dates and branch boundaries are in [data sources](references/data-sources.md).

Keep the provider split:

- KEV handles multi-candidate combat card and potion choices. The controller validates the map route and reduces movement to its sole reachable next node, then selects that legal node deterministically without a model call. KEV receives only current live tactical state; never attach Luna's Skill, strategic hypotheses, or confirmed-pick ledger.
- GPT-6 Luna is reserved for meaningful strategy: full map-route planning, card reward selection, shop purchases, and other strategic choices. For those operations only, use the sibling [Luna-only Ironclad Skill](../sts2-ironclad-luna/SKILL.md), including its deck-aware three-card comparison and bounded `luna_context` updates.
- At card rewards, compare every offered card with the live deck and `skip`. Do not add a card just to grow the deck: skip when none fills a current role, completes an existing engine, or answers a near-term threat.
- Use deterministic handling when a screen has one legal action or only routine progression, including the sole next node on a validated route. Never spend a Luna or KEV call to replay a fixed action.

Treat “claim a post-combat reward” and “choose one offered card” as different game screens and actions. Treat “plan a route” and “move to the next node on that route” as separate operations. Validate every action against the current legal action set before submitting it.

In combat, use the live same-turn complete lines in `combat_policy`. Each line is one feasible sequence under one shared Energy budget and reports actual enemy HP damage after Block, attacks canceled by kills, incoming HP loss after Block, self-cost, and resources spent. Keep enemy attack damage and card-paid HP loss separate: Block only prevents the former. The local filter uses a global Pareto frontier; it never subtracts player HP loss from enemy HP damage with a fixed exchange rate. Remove a line only when another exact line is no worse on actual enemy HP damage and uncapped player HP loss, with at least one strict improvement. If an exact line survives, known-lethal lines are excluded; if every exact line is known lethal, keep the minimum-loss result and check unresolved rescue actions. Preserve genuine attack/defense and setup/tempo tradeoffs for KEV, which receives the live HP margin, intents, enemy HP/Block, kills, and line outcome vector. Before submitting `end-turn`, use any legal card that measurably reduces this turn's incoming HP loss after including that card's own HP cost; then reread state and let KEV choose the next action. This also applies as a best-effort first step when one block card alone does not prove survival.

For Ascension 0-2, use effective damage as a run-level drafting and tempo plan, not an automatic action preference each turn. A hit that only clears enemy Block, cannot be converted by the same-turn line, does not kill or change a threat, and has no confirmed side effect is not progress. Each exact line compares post-turn HP with that line's remaining unblocked visible attack damage; it is marked `critical` if HP would not withstand a repeat of that same threat. This is a conservative same-threat stress proxy, not a next-turn forecast or a fixed HP-percentage rule. `critical` is a warning to inspect whether mitigation materially improves the current survival margin; do not ignore it, and do not treat it as a command to block when the defense line gives up a kill or substantially greater threat reduction. `usable` does not mean to attack or permit an arbitrary HP trade. Compare actual enemy HP damage, HP loss prevented by Block, kill-canceled attacks, enemy remaining HP, and Energy opportunity cost. Choose material mitigation when it prevents meaningful loss and the damage line does not justify giving that up; choose damage when threat is light and it materially shortens or ends the fight without surrendering more valuable defense. Do not force either side based on reserve band alone. Burning Blood heals only after combat.

The evaluator resolves supported fixed, multi-hit, AoE, and X-cost attack profiles against each target's live Block and HP; Strength applies per hit and X-cost hits use Energy remaining when played. Main v0.107.1 `SetupStrike` applies its temporary Strength after its own hit, so only later attacks in that same line can benefit. A zero-hit X attack is zero damage even if another modifier is present. Remove an exact Block-chip attack when its best supported full line still deals no enemy HP damage; an affordable follow-up alone does not prove conversion. Temporary or persistent Strength must increase enemy HP damage in the supported current-turn line or have another confirmed immediate effect. Strength that begins at the next turn start (for example, Demon Form) must not be applied to this turn's attack math; a Strength-only card with no current payoff is filtered. Future draw/discard piles are audit context only; never play a pure Strength card solely because future attacks are visible. Unknown multi-turn Powers stay unresolved rather than receiving invented outcomes. Do not spend Energy to make the hand look used. A kill's defense value is only the incoming attack damage it actually cancels. Never choose known lethal self-cost if an exact surviving line exists; reread live state and legality after each submitted action. This is a bounded turn evaluator, not a multi-turn fight solver. See the [Ironclad playbook](references/ironclad-playbook.md); exact values and intents come from the live snapshot.

The run log's `luna_context` belongs only to Luna's existing strategic calls. KEV never receives it; combat decisions use the newly observed hand, piles, intents, relics, potions, `combat_pressure`, and `tactical_order`. Current live game data always overrides a Luna hypothesis. Never make an extra Luna request for ordinary combat.

Pause on incomplete or stale state, unknown game version, wrong/missing character, unsupported target type, illegal provider output, and a route that is no longer reachable. Follow the configured confidence policy for the current operation. On action timeout, re-read state and do not retry the POST because the first action may have succeeded. The default project setting is dry-run; do not enable game actions unless the user explicitly requests live play.
