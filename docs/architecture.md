# Architecture and action contract

## Components

1. **Game Mod bridge** — `vendor/STS2MCP/` is the actual game-side C# Mod plus an optional Python MCP wrapper. The locally patched Mod source is version 0.4.4, targets installed Main v0.107.1, and exposes a REST bridge at `http://127.0.0.1:15526`; the project requires passive bridge schema 2 before it consumes `GET /api/v1/singleplayer?format=json` and `POST /api/v1/singleplayer`. Its additive `player.deck` field supports Luna's deck-aware strategic choices.
2. **State normalizer** — `src/sts2_agent/state.py` checks current screen and required screen fields, fingerprints the raw state, and pauses for unknown or incomplete data.
3. **Legal action builder** — `src/sts2_agent/actions.py` builds candidates from the current game payload, uses the Mod's current indices and entity IDs, omits unaffordable/locked options, and rejects unsupported targeting types.
4. **Provider adapters** — `providers/kev.py` consumes only structured KEV choice probabilities and its operation-specific live state; `providers/luna.py` consumes strict JSON from OpenAI Chat Completions and the Luna-only Skill/context for strategic reads; `providers/mock.py` provides offline plumbing demonstrations.
5. **Controller and MCP tools** — `controller.py` selects the provider, checks confidence and legality, creates short-lived proposals, re-reads state before submission, paces action POSTs, and never retries an ambiguous POST.

The upstream Python server is not the source of game state by itself: the C# Mod must be present and loaded in the game. The project MCP wraps the same REST bridge and adds routing, validation, and dry-run defaults. Do not start the upstream MCP sidecar alongside this controller against the same game unless intentionally testing one client at a time.

State reads are allowed only after the harmless root health response advertises schema 2. The controller refuses older bridges before requesting game state because the upstream v0.4.0 snapshot builder can open shop inventories and treasure chests while reading. The local Mod patch is described in [local-mod-patches.md](local-mod-patches.md); it must be built and loaded by restarting the game before live state reads resume.

## Provider routing

| Screen/action | Provider | Reason |
| --- | --- | --- |
| Combat card play / potion / multi-choice hand selection | KEV | Fast tactical candidate classification from legal actions only. |
| Planned map-route next step | Deterministic | Luna already fixed the route and the controller filters to its sole currently legal next node; no model call is needed. |
| Full map route planning | GPT-6 Luna, once per map graph | Compare the full map path with deck, HP, and route context; cache the validated route and do not ask Luna again while following that graph. |
| Card reward selection or skip | GPT-6 Luna | Evaluate a new card against the current Ironclad run. A `rewards` screen claim only opens this selection screen; the actual card choice is a separate action. |
| Shop purchases, event/rest/relic/treasure/deck-choice strategy | GPT-6 Luna | These are run-level economic or strategic choices. |
| Forced one-action screens, event dialogue, reward collection, `proceed` | Deterministic | No model call when there is no meaningful choice. Rewards are claimed one at a time; card choices remain separate. |
| Unplanned map movement | Paused | Luna must create a legal route first. Planning and execution are distinct. |

In live mode, the only strategic operations sent to Luna are those that present a genuine choice. If no credential is present, Luna-required operations pause; they never fall back to another model. The `provider_mode = "mock"` setting overrides provider routing for safe interface demonstrations.

## KEV contract

The adapter sends `POST http://127.0.0.1:8009/v1/systemone` with `state`, `model = "kev-latest"`, and one `choice` question. Outside combat, `criteria` maps legal action IDs to descriptions. During combat, each category is a complete-turn-line ID and its criteria contains the first legal action, the planned step prefix, the full modeled line, and that line’s outcomes. A valid reply still follows the structured schema below; the selected combat line is mapped back to its current legal first action before the controller can submit anything.

```json
{
  "answers": {
    "action": {
      "choice": "turn-line:4",
      "probabilities": { "turn-line:4": 0.81, "turn-line:5": 0.19 },
      "confidence": 0.81
    }
  }
}
```

Real responses include every choice-category ID in the probability map. Outside combat those are exact legal action IDs; in combat they are complete current-turn line IDs. The adapter maps the chosen line to its exact legal first action and aggregates line probabilities by first action for the dashboard. It checks exact keys, chosen ID, numeric bounds, and approximate probability sum. Upstream defines Choice confidence as `(p_max - 1/K) / (1 - 1/K)` for `K` options: it measures concentration above a uniform distribution, not the probability an action is correct or feasible. Several equally serviceable choices can therefore produce a low score. Combat uses a `0.0` selectivity floor so probability spread alone does not stall play; every submitted game action is still checked against a fresh matching MCP state. Luna strategic choices keep their separate confidence floor. A confidence value is not a calibrated guarantee of correctness. KEV never calls `/v1/chat/completions` or invents action text. Standard requests use `/v1/systemone`; optional permutation averaging is off by default because it adds latency and is a local-only capability. When enabled, the adapter checks `/v1/models` for the local exhaustive-mean capability and permits 2–4 categories only.

For combat, the controller applies a local candidate policy to the exact live legal-action list. KEV receives a compact whitelist of current hand, HP/Energy/Block, enemy intents/status, relics/potions, pressure, and one summarized outcome row per complete current-turn line. Supported fixed, multi-hit, AoE, and X-cost attack profiles are evaluated against each target's HP and Block one hit at a time; X hit count uses Energy remaining at play. A zero-hit X attack is exactly zero damage even if an unrelated Vulnerable modifier would make nonzero attacks uncertain. Damage modifiers, random/conditional targets, variable formulas, mixed effects, and unknown relic interactions remain explicitly uncertain. A zero-output action is removed only when its damage/block result is exact and it has no modeled secondary effect; an incomplete estimate is never treated as proof of uselessness. A paid temporary or persistent Strength action compares the best complete affordable attack sequence with and without its Energy cost, including per-hit Strength and enemy Block. A Strength-only action without measured current-turn enemy HP-damage increase is removed; future draw/discard piles stay in audit logs and are excluded from KEV's action context. After each submitted step the controller rereads MCP state, rebinds the next card/potion by live identity rather than old slot/index, and checks the current legal set. If that move is no longer legal or the selected prefix has reached an uncertainty boundary, it drops the continuation and asks KEV against the fresh board. Its payload rejects `luna_context` and legacy `run_memory`; the Luna Skill, pick priors, strategy hypotheses, and confirmed strategic history are not sent to KEV. Equivalent physical copies are grouped by live card identity, upgrade/cost/text/modifiers, and target so they do not distort KEV's category probabilities. Exact kill value includes only current attacks that the kill actually cancels; it does not bypass the complete-line comparison. Every uncertain nonzero effect remains labeled for KEV, while a proven zero-output action may not be selected just because it is an Attack.

`turn_line_candidates` first flattens every per-first-action `joint_turn_lines` frontier, then compares complete lines globally. Exactness belongs to the actions in a selected line: an unmodeled potion or another unchosen legal action stays as an unresolved branch and does not make two separately simulated lines uncertain. A selected line remains unrankable when its own effects, damage modifiers, or enemy intent are uncertain. Exact lines use a global Pareto frontier, never a scalar `enemy HP damage - player HP loss` score. A line is pruned only when another exact line deals at least as much actual enemy HP damage and causes no more uncapped player HP loss, with at least one strict improvement; resource cost can prune exact outcome ties. A speculative future effect cannot rescue a line that is worse on exact current outcomes. Known-lethal lines are removed if an exact surviving line exists. If every exact line is known lethal, the minimum-uncapped-loss outcome is retained and unresolved rescue actions remain available. Genuine attack/defense/setup trades stay visible to KEV, which receives current HP, intents, enemy HP/Block, killed threats, and separate line outcome fields. Each exact line also compares post-turn HP with its own remaining unblocked visible attack damage; a nonpositive margin is marked `critical` as a conservative same-threat stress proxy, not a next-turn forecast. On A0-A2, front-loaded effective damage is a run-level drafting and tempo plan, not a default action preference for each turn. The `usable` reserve band only says the line is outside the stress marker; it does not bonus attacks or allow arbitrary HP trades. KEV compares actual HP damage, HP loss prevented, kill/cancel value, enemy remaining HP, and Energy opportunity cost; it can choose material defense over small nonlethal damage. If one meaningful first action remains, the controller takes it directly; KEV handles only remaining tactical alternatives and unresolved branches. If a line stops at an uncertainty boundary, KEV decides again from the reread state. Strength/Power assessments include `setup_payoff_evidence` with measured current-turn attack HP damage before/after setup and Energy cost; future piles remain audit-only and are not sent as reasons to play. Known pure Strength-only cards without measured same-turn enemy HP-damage increase are filtered before KEV. Main v0.107.1 `SetupStrike` is parsed as an attack that applies temporary Strength after its own hit; if its complete affordable line still produces zero enemy HP damage, it is removed even when an affordable follow-up exists but cannot penetrate remaining Block. The bounded search supports fixed, multi-hit, AoE, and X-cost attack profiles plus supported pure Block and exact Strength effects; it applies enemy Block before HP, HP caps, and cancellation of the killed enemy's current attack. Draw, potions, mixed-effect cards, arbitrary modifiers, and unparsed state remain uncertain and are listed as unresolved. These are bounded current-turn lines, not a full fight solver.

Before KEV inference, provable no-effect actions and Pareto-dominated exact complete lines are removed. Exact line comparison includes actual enemy HP damage, incoming HP loss after Block and kill cancellation, uncapped player HP loss including self-cost, energy spent/left, and known setup effects; it never combines the best-damage and best-survival extremes from separate sequences. Unknown alternatives remain available but do not contaminate the selected line's exact result. Line IDs, separate outcome dimensions, uncertainty scope, dominator, outcome differences, and full assessments are logged. KEV chooses among genuine attack/defense/setup tradeoffs and unresolved actions; the local filter does not decide that one point of player HP equals one point of enemy HP.

The tactical policy is intentionally split: deterministic code proves legal sequences, current-turn math, lethal/safe boundaries, zero effect, and strict dominance; KEV weighs the remaining context-dependent trades. The Main v0.107.1 Ironclad strategy sources support neither “always attack” nor “always block” and do not provide a universal damage-to-HP conversion. The model sees current HP, enemy intents and remaining HP, actual damage after enemy Block, actual HP loss after Player Block, kill-canceled attacks, and a line-specific same-threat reserve band. Live estimates do not certify unmodeled card/relic effects, and the controller re-reads state before submission. A transient KEV transport failure can be retried up to two times only after a fresh complete MCP read proves the exact state fingerprint, game version, and character are unchanged; a state change aborts the retry and restarts decision-making without a game action POST. Game action POSTs themselves are never retried after an ambiguous result. `combat_policy`, the complete original legal IDs, retained/suppressed provider IDs, removal reasons, duplicate collapses, assessments, guard reasons, dominator proof pairs, separate outcome dimensions, and estimated HP outcomes are logged for review.

Combat policy correction after the 2026-09-24 review: the v16 prompt said to prefer attacks when reserve was usable; v17 removed that attack bias and clarifies that usable is only a risk annotation, not a move preference. A run-log review then found a structural failure: KEV could choose an opening because its forecast relied on a follow-up, but a separate next-step call could end the turn and abandon that sequence. KEV now selects a complete current-turn line. The controller validates/rebinds every submitted step and stops the automatic prefix at the first unsupported effect, then asks KEV again from the newly read state. Setup payoff and future-pile uncertainty stay explicit. Exact no-value actions and a narrow lethal-survival guard remain local; non-dominated damage/survival trades stay model-selected. The evaluator remains bounded, not a full fight solver. `game_over` is a complete terminal state and exposes only the upstream-advertised `main_menu` action.

Combat policy correction v18 after review of “attack for attack's sake” and setup cards: v17 had removed the attack preference in principle but still sent KEV an A0-A2 tempo profile and conditional reserve-band wording. KEV now receives neither Ascension nor the run-level combat profile; that strategy stays in Luna's Ironclad Skill. The local evaluator models live Vulnerable status and the branch's 1.5 damage multiplier, and recognizes pure Vulnerable setup such as Tremble as a target-specific same-turn effect. It measures the best affordable attack sequence before and after the setup cost; a pure Vulnerable or Strength card with no proven increase in enemy HP damage is removed when a legal fallback exists. Existing Block-chip filtering remains in place. KEV sees the remaining complete-line tradeoffs with a direct rule: meaningful damage prevented by Block usually outweighs a small nonlethal hit; favor damage when it advances or ends the fight and the lost defense is immaterial. No fixed damage-to-HP exchange is used. Luna's reward Skill now treats Skip as the baseline and declines filler cards when no offer improves a current role, existing engine, or near-term matchup. v18 is offline-verified only until a new live fight is available.

Combat policy correction after the subsequent user review: per-action dominance retained a bad first action whenever one action had a high-damage line and a separate low-loss line, even if another complete line dominated the specific setup/Block line. The controller now builds a global frontier across all exact complete lines before presenting categories to KEV. A line is removed only when another single complete line deals at least as much enemy HP damage and takes strictly less total HP loss; supported future Strength cannot rescue a strictly inferior current-turn outcome. Exact ties may retain visible repeated-attack setup only when it does not worsen current damage or HP loss. If only one legal first action survives, the controller uses it directly. The regression suite includes a Strength line that deals no damage while a Strike+Block line deals damage without extra HP loss, a zero-damage attack into Block with useful Defend available, and a real Attack-versus-Block trade that remains for KEV.

Combat policy correction after the v15 overfit review (`tempo-risk-setup-v16`): a future pile with multiple Attacks still does not make a pure Strength card a current combat action. Without measured same-turn enemy HP damage or another confirmed immediate effect, the Strength-only play is removed; future-pile facts remain in local audit data and are not sent as KEV payoff context. Strength that begins at the next turn start (such as the installed `Demon Form` text) is not applied to the current attack line, and its own setup action is filtered when it has no current payoff. A0-A2 effective damage is a run-level drafting and fight-tempo plan, not a per-turn attack default. In v17, usable is only a same-current-threat stress annotation; KEV compares actual HP damage, HP loss prevented by Block, kills, enemy HP, and Energy opportunity cost. To avoid an unsupported fixed HP percentage, each exact line labels its remaining-HP margin against the unblocked current attack threat on that same line; this is a conservative stress check, not a prediction of the next turn. Neither action is forced by the reserve band; select the line by actual damage, avoided HP loss, kill value, remaining enemy HP, and Energy opportunity cost. The exact zero-damage attack filter, full-line comparison, action legality check, and post-action state reread remain in force.

`luna_context.strategy` stores Luna's bounded run hypothesis and priorities; `luna_context.confirmed_run_items` stores cards/relics confirmed by accepted game choices. The controller sends this context only on an existing Luna strategic request. Strategic Luna contexts include the live `player.deck`, and card rewards pause if the complete deck is absent or malformed. After a route is validated, the controller reduces each movement step to exactly one planned legal node and selects that node deterministically; any other count pauses without a provider call. The full live state always outranks Luna's hypothesis. No provider call is added to route execution.

## Luna contract

Base URL: configure your own OpenAI-compatible endpoint in `config.toml` (the example uses loopback). Request URL: `POST /chat/completions` (the base URL includes `/v1` once). Headers: `Authorization: Bearer $STS2_LUNA_API_KEY`. The adapter sends model `gpt-6-luna`, temperature `0`, and JSON-object response format. Decision and route responses return a bounded `luna_context_update` object (or `{}`); the selected `action_id` must exactly match the current legal-action list. Route responses contain only future nodes, begin with a currently reachable `next_options` node, follow graph edges, and end at a listed boss; the controller validates all of these conditions before applying a Luna-context patch.

Allowed `luna_context_update` keys are `archetype_hypothesis`, `win_condition`, `supporting_signals`, `missing_roles`, `upgrade_priorities`, `combat_rules`, and `avoid`. Values are bounded strings/lists. Luna cannot populate confirmed card/relic facts; the controller records those only after the game accepts an indexed card/relic choice. Accepted Luna strategic actions commit the update to the run JSON log for Luna's next strategic read; KEV never reads it. Luna is called only for existing strategic operations, so this adds no per-card-combat request.

On 2026-09-23, the process-only SSH key handoff was used to verify the authenticated `/v1/models` response and a real card-reward choice through this MCP adapter. The first route response failed the reachable-first-node validation; it was logged and did not move the character. Credentials and raw HTTP request bodies are not written to the repository, run logs, or monitoring UI.

## Codex model-selector limitation

The supplied Luna endpoint exposes OpenAI Chat Completions. Current official Codex model-provider configuration lists `responses` as the only supported `wire_api` value. Therefore this endpoint is not added as Codex's own primary model provider. Codex stays on its existing model; the local project MCP calls Luna through the adapter above. See the official [Codex Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference) for the current `model_providers.<id>.wire_api` contract.

## Proposal and safety behavior

- Every proposal records the current state fingerprint and expires after `max_state_age_seconds`.
- When game actions are enabled, execution re-reads the game and requires an identical fingerprint and still-legal matching payload.
- `game_actions_enabled = false` returns a dry-run response without POSTing the game action.
- Each `step_once` creates or submits at most one proposal/action. The bounded `autoplay` MCP tool chains these guarded steps immediately after each action settles. It reuses the settled snapshot to start the next decision without a redundant state read, then still rereads and validates immediately before the next action POST. A 450 ms minimum applies only between game-action submissions if inference finishes sooner.
- After a successful action POST, the controller polls read-only game state for up to two seconds for screen transitions to settle. It never repeats the action POST while waiting. If the resulting state is incomplete, or its fingerprint is unchanged from the submitted state, autoplay pauses before requesting another decision or sending another action. The guard compares pre/post fingerprints, since action IDs can be reused after the hand or screen changes.
- When a combat transition reports a known transient missing-player/battle snapshot, autoplay continues read-only polling for up to 45 seconds for the next complete screen/player phase. A failed or incomplete poll never authorizes another action POST.
- On action POST timeout or connection loss, outcome is unknown. The controller may read the state once for reconciliation, reports what changed, and never retries the POST.
- Unsupported screens, missing run/character data, non-Ironclad character, version mismatch, invalid targets, malformed provider responses, low confidence, or stale state stop the step.
- Shop inventory close and treasure chest open are distinct, explicitly advertised actions. A shop can be left only after its inventory is closed; no provider may infer a hidden close/proceed control.
- A missing route ID, no longer reachable route node, or invalid edge invalidates the map plan. Route execution never chooses a new node outside the plan.

## MCP surface

- `preflight`: read-only game bridge, installed version, KEV model listing, Luna key readiness.
- `get_game_snapshot`: current normalized and raw state.
- `get_legal_actions`: candidate actions for the current screen.
- `plan_map_route`: Luna plan (mock BFS in mock mode); it does not move the game.
- `recommend_next_action`: one provider-validated proposal.
- `execute_proposal`: revalidates a proposal; dry-run unless enabled in local config.
- `step_once`: combines one proposal and, when enabled, at most one action submission.
- `autoplay`: runs up to 20 immediately chained actions per call, plans one complete route per map graph, and stops on an incomplete/stale state, provider error, invalid action, unknown POST outcome, or terminal screen.

Each run has a JSON audit log under `runtime/runs/`. It records the provider input state, full legal set and policy-filtered candidates, KEV probability output, chosen action and explanation, validation receipt, game response, resulting state, Luna-only `luna_context`, and any combat-policy or survival-guard override; credential-like fields are stripped and raw HTTP bodies/prompts are not stored. KEV and Luna provider inputs remain independently scoped. The dashboard offers the latest JSON for download. The bounded `scripts/autoplay_mcp.py` runner calls the MCP tool repeatedly until it pauses, ends, or reaches its configured action cap. It creates a temporary live-action config and removes it on exit; checked-in examples stay dry-run.

Routes and pending proposals are in-memory state of the MCP process. Restarting MCP clears them; the next map step will request a fresh Luna plan for that map graph.
